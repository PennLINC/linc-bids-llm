Inside the PennLINC Assistant

The assistant troubleshoots the lab's BIDS Apps the way a maintainer would. It checks whether someone already hit the problem, reads the docs, and then reads the code at the version the user actually ran. Every answer links back to its sources. This guide covers the machinery: what it ingests, how that text is indexed and searched, how the agent works, and how your feedback becomes tests.

§0 · Overview

The whole machine

Two pipelines meet at a pair of stores. Every night an ingest job turns docs, issues and forum threads into a searchable index and refreshes copies of each app's code. Each question then goes through a router to one of two answer paths, and both read from those stores.

  • Text is searched two ways, by meaning and by exact words, and the two result lists are merged.
  • Code is never embedded. The agent greps the real source at the release the user ran.
  • Everything is cited. Answers link to issues, threads, docs lines, or code lines pinned to a release tag.
  • Every rating is reproducible. Feedback records the models, the code commit, the index build and the chat.

§1 · Ingest

What it reads

For each app, three kinds of text go into the index: the repo's docs, its GitHub issues, and its NeuroStars threads. Code is kept separately as plain git checkouts.

Docs

Files in the app's docs folder (vignettes/ for ModelArray) at its latest release tag, plus the top-level README. Answers should describe the release people run, and the tag goes into every docs link.

  • Formats.md .rst .txt .Rmd
  • Skippedbinaries and files over 1 MB
  • Callslatest release → its commit → file tree → each file

GitHub issues

Every issue, open and closed, with all of its comments. Pull requests are left out.

  • Droppedbot comments (CI, codecov) and empty ones
  • Clippedany post over 6,000 characters
  • Solvedclosed with the reason “completed”

NeuroStars

Every topic under the app's forum tags, read through Discourse's JSON API. XCP-D collects three tags: xcp_d, xcpd and xcp-d.

  • Orderquestion, accepted answer, other replies
  • Droppedreplies under 25 characters, moderator actions
  • Pace1 request per second; honors Retry-After

Source code

Shallow clones of the five newest stable releases and main for each repo. None of it is embedded. The agent greps and reads these files while it answers.

  • Skippeddrafts, pre-releases, release candidates
  • Sortedby version number, not by date
  • mainre-fetched every night

Which repos a question searches

Each card searches its own repo plus any configured neighbors, so questions at the boundary between two tools still find the right threads. Neighbors are set in config.yaml.

  • qsiprep cardqsiprep · qsirecon · qsiplan
  • qsirecon cardqsirecon · qsiprep
  • modelarray cardmodelarray · modelarrayio
  • aslprep cardaslprep
  • xcp_d cardxcp_d
  • cubids cardcubids

Turning a thread into one document

Before anything is cut up, each issue or forum topic becomes a single markdown document. This is the start of qsiprep issue #703 as the index stores it.

§2 · Ingest

Cutting documents into chunks

Search works on chunks of about 500 tokens, not whole documents. The chunker packs whole lines into windows, so every chunk knows exactly which lines it came from. That is what makes line-level links to the docs possible.

SettingWhat it does
WindowAbout 500 tokens, counted with OpenAI's cl100k tokenizer. A single line longer than that becomes its own oversized chunk.
OverlapAbout 75 tokens of whole lines repeat at the start of the next window, so a fact that straddles a boundary appears whole in at least one chunk. Before a long line the overlap shrinks to make room for it, so every chunk reaches past the one before.
HeadingsA markdown heading (# to ######) starts a new section, and windows never cross one. reStructuredText titles are underlined instead, so .rst files like this one are cut by size alone.
Docs linksblob/<tag>/<path>?plain=1#L<start>-L<end>. The ?plain=1 forces GitHub's code view; its rendered view ignores line anchors.
Thread chunksKeep the thread's URL. Every chunk after the first gets # <title> put in front, so a lone comment still says what it is about.
IDsA hash of app, source, document and position, for example sha1("qsiprep:issues:#703:4"). Re-ingesting a thread reproduces the same IDs.

Chunks per document: docs average 7.8 (median 2.5; a changelog reaches 201), issues 3.3, NeuroStars threads 7.4.

§3 · Ingest

Two indexes, written together

Every chunk is stored twice. One index finds text with similar meaning, the other finds the exact words. Both are written in the same step, so they always hold the same chunks.

Meaning

Vectors in Chroma

A small local model, BAAI/bge-small-en-v1.5, turns each chunk into 384 numbers. Chunks about the same thing land close together even when they share no words. It runs on the server's CPU, so embedding costs nothing and no text leaves the box.

qsiprep #703, the “## Summary” chunk
[-0.0692, -0.0254, -0.0376, -0.0448, -0.0200, -0.0697, … 378 more]
length 1.0 · compared by cosine distance · HNSW graph index

Questions are embedded with BGE's search instruction in front, Represent this sentence for searching relevant passages:, and chunks without it. That asymmetry is how the model was trained to be used.

Keywords

BM25 in SQLite FTS5

A full-text table with Porter stemming, so running matches run. BM25 ranking rewards rare words, and flag names, file names and error strings are exactly that.

question  dwiextract: [ERROR] No b=0 volumes present
query     "dwiextract" OR "error" OR "no" OR "volumes" OR "present"

Each word is quoted, so punctuation in a pasted error can't break the query. One-character words like b and 0 are dropped, and only the first 80 words of a long paste are used.

What one stored chunk looks like

NeuroStars chunks carry the topic ID, whether it has an accepted answer, reply and view counts, and ns_bumped, the time of the last activity, which drives syncing (§5). The whole index is about 150 MB on disk. Each night it is also published as the index-latest GitHub release asset, so a laptop can download it instead of rebuilding.

§4 · Retrieval

Hybrid search and rank fusion

A search asks both indexes for their 40 best chunks and merges the two ranked lists with reciprocal rank fusion (RRF). The top 8 go to the model.

score = 1 / (60 + rank in the vector list) + 1 / (60 + rank in the keyword list)

A chunk missing from a list gets nothing from it. Ranked first by one side only, a chunk scores 1/61 = 0.0164. Ranked 3rd by one side and 7th by the other, it scores 1/63 + 1/67 = 0.0308 and wins. RRF uses ranks, not raw scores, so the two very different scoring scales never need to be compared. The 60 is the standard constant; it keeps rank 1 from dwarfing rank 5.

Both sides use the same scope filter: the card's app plus its neighbors.

§5 · Ingest

Staying current

A timer on the server rebuilds everything at 03:30 UTC each night. Ingest is incremental, so on a typical night it fetches and re-embeds only what changed since the last run.

SourceWhat counts as a changeWhat happens
DocsThe latest release tag points to a different commitThat app's docs chunks are deleted and rebuilt from the new tag
IssuesUpdated after the stored watermark (GitHub's since=)Each changed thread is deleted and re-added; the watermark moves to the newest update time
NeuroStarsA topic's bumped_at changedChanged topics are replaced; topics that disappeared are removed
CheckoutsA new stable release, or new commits on mainNew tags are cloned; main is fetched and hard-reset
EverythingThe embedding model or the chunk settings changedFull rebuild, because mixing embeddings from two models silently breaks search

The bookkeeping lives in index/manifest.json. Today's, abridged:

The nightly run

The job runs at low CPU and disk priority with single-threaded math libraries. If the 2 GB server runs short of memory, the kernel kills the refresh before the app.

§6 · Answering

Two answer paths

A router sends each question down a cheap one-call path or the agent path. The rules are a few lines of plain code, and the sidebar can override them.

Of the 48 opening posts in the held-out test set (§11), the router sends 17 to one-shot and 31 to the agent; most of those 31 are long pastes. All three searches in the fusion explorer route to one-shot. “What does --output-resolution do?” goes to the agent, because its top hit (#681) is an open issue.

The one-shot path

One call to gpt-5.4-mini with the 8 chunks the router already retrieved, numbered so the answer can cite them as [1] or [2][4]. The Sources list under the answer shows all 8.

SYSTEM  You are a troubleshooting assistant for the qsiprep BIDS App, answering a member of
        the lab. You are given numbered context chunks retrieved from past GitHub issues,
        solved NeuroStars threads, and the docs.
        - Prefer answering from the context; cite chunks by their bracket index like [1] or
          [2][4], and only cite chunks you actually used.
        - You may add practical diagnostic reasoning, but label anything not supported by
          the context as such.
        - If the context does not actually answer the question, say so and ask for the
          version, exact command, and full traceback.
        - Be concise and practical; give the steps, not a preamble.
        Important package facts (authoritative — trust these over any older/ambiguous
        retrieved text):
        - (qsiprep) qsiprep does DWI PREPROCESSING only. Reconstruction … moved to the
          separate qsirecon package … A recon_spec.yaml is passed to qsirecon, not qsiprep.
        - (qsirecon) qsirecon does RECONSTRUCTION / post-processing of qsiprep outputs …
        Today's date: 2026-10-05.
USER    Context chunks:
        [1] [ENH] add --prefer-gpu — issues (solved)
        https://github.com/PennLINC/qsiprep/issues/725
        …chunk text…
        [2] Eddy error when using GPU — issues (solved)
        …
        Question: eddy is taking forever, can I use the GPU version?

This prompt is about 2,300 tokens, so a one-shot answer costs roughly a third of a cent. The “package facts” come from config.yaml and are added to both paths' instructions whenever that app is in scope. They exist to correct known confusions; this one keeps reconstruction questions away from QSIPrep, which no longer does reconstruction.

§7 · Answering

The agent

The agent works a question like a maintainer triaging an issue: search the history, find the raising code at the user's version, read it, and cite it. It runs on gpt-5.6-terra, a reasoning model, through OpenAI's Responses API.

ToolWhat it doesLimits
search_kb
query, source_filter?		The hybrid search from §4 over the card's scope, optionally only issues, NeuroStars or docsTop 8; each with title, URL, solved flag and a 240-character snippet
grep_code
pattern, version?, regex?		ripgrep over the checkout for that version. Literal text by default, case-insensitive unless the pattern has capitals15 matches per file, 80 lines in all, 300 characters per line
read_file
path, version?, start?, end?		Numbered lines plus a GitHub link to exactly those lines, pinned to the tag (or to main's commit)400 lines per call; paths outside the checkout are refused

All three are read-only. The model gets no shell and no network access beyond these calls.

Which code does “1.0.1” mean?

Users often run old containers, so the agent greps the release they ran, not main. A stated version maps to the nearest checkout on disk. The table shows why it matters: the same error line sits at a different place in different releases, and it no longer exists on main.

What the agent is told

  1. Call search_kb first. Someone may have hit this already, in a closed issue or a solved thread.
  2. For a code question or a traceback, grep_code the user's version to find the raising line, then read_file it to get a permalink.
  3. Use a version stated anywhere in the chat and don't ask for it again. If none was given and it matters, ask before grepping. Say when a fix landed in a later release.
  4. Cite every claim by URL or permalink, and label reasoning that goes beyond the sources.
  5. Never invent APIs or error messages; check them with the tools.
  6. Separate a confirmed cause (the raising code, or a matching solved thread) from diagnostic guidance. If the cause can't be confirmed, give the guidance and then a GitHub issue draft with Version, Command, Traceback, What was tried, and Suspected code path, plus a reminder to search open issues for a duplicate first.

What it remembers of the chat

The agent sees the last 12 messages, plus the chat's opening message once it has scrolled out of that window, because that is usually where the version and the original error are. Each question also gets a one-line note about the version. When the user gave one two turns ago, the note reads:

(Earlier in this chat the user mentioned '1.0.1', which may be the version — do not ask for it again; confirm only if it is ambiguous.)

The one-shot path takes no history, which is why the router sends every follow-up to the agent.

§9 · Operations

Cost and guardrails

Only writing the answer costs money. Embedding, search and grepping all run on the server for free.

One-shotAgent
Modelgpt-5.4-minigpt-5.6-terra
OpenAI APIChat CompletionsResponses
Price per 1M tokens$0.75 in, $4.50 out$2.00 in, $12.00 out
Calls per answer1Up to 12 with tools, plus 1 wrap-up
Cost per answerAbout 0.3¢ to 0.4¢3.6¢ for a short run measured October 5; long hunts can reach 20¢ to 25¢

The agent varies because every turn re-reads the conversation so far, including all earlier tool output. The short run used 4 model calls and 10,646 input tokens. A long hunt like the 13-call run in §8 returns about 15,000 tokens of tool output; re-read turn after turn, that comes to roughly 100,000 input tokens. OpenAI bills input it has seen recently at about a tenth of the price (3,978 of the short run's tokens were billed that way), but the app's meter counts all of it at full price on purpose.

  • A daily ceiling. Each model call's token usage is priced and added to the day's total (UTC). Once it reaches $300, the app stops answering until the next UTC day. This is the only hard cap; OpenAI offers this account no enforced limit.
  • Pricing that fails safe. A model missing from the price table is charged at $5 in and $15 out per million tokens, so a config mistake over-counts rather than under-counts.
  • Access. HTTPS through Caddy with one shared password, on a single 2 GB Lightsail server that costs $12 a month.
  • Read-only tools with size caps, and no way for read_file to leave the checkout.
  • A testing-phase notice. Chats are saved on the server for evaluation, so nothing personal or sensitive goes in.

§11 · Learning

Evaluation

One harness, eval/run_eval.py, scores two kinds of test cases: problems the lab already solved, and cases promoted from your feedback.

Held-out set: does the thread that solved it come back?

48 solved QSIPrep cases: 24 issues closed as completed and 24 NeuroStars threads with an accepted answer. Half come from the older half of each history and half from the newer, so old phrasing is tested too. The query is the thread's opening post, and the target is the thread's URL.

Read these numbers with care. Each query is the thread's own opening post, and that thread is in the index, so the exact words are there to match. That favors keywords, and BM25 alone does as well as hybrid. This test can't show what vectors add on reworded questions, like the b=10 example in §4. Tester cases with a correct URL can.

The August slides showed vector-only at 0.41 and BM25-only at 0.38. Those two numbers came from a scoring bug that read the single-method lists out of rank order. It was fixed on October 5 (6114b85), and the hybrid number did not change.

Regression set: from a thumbs-down to a test

When the correct URL isn't in the top 8, the report says which of three things went wrong. The thread isn't in the index at all (a gap in what we ingest). It's indexed under an app outside the card's scope (a neighbors question). Or it's indexed and in scope but ranked too low, which is the only case that tuning search can fix. URLs are compared by a normalized key, so a pasted link ending in #issuecomment-… or a NeuroStars post number still matches.

Grading answers with a judge

run_eval --answers N asks each question again through today's router and paths. Then gpt-5.4-mini judges the new answer against the reference: the historical fix for held-out cases, or the tester's note for feedback cases. The judge reads the whole answer (up to 12,000 characters, keeping the start and the end) and the earlier turns of the chat. Each case is judged five times and passes only if all five pass. A split verdict is labeled, for example [judge split: 3 of 5 runs passed], and left for a person to read.

The judge is dependable when the tester's note is specific. With a vague note it wobbles, and setting the temperature to 0 only hides the wobble. On held-out cases it is pessimistic, because it compares against fixes that may be years old.

§12 · Status

Rough edges and what's next

  • Near-duplicate chunks, fixed October 7. When a few short lines came right before one very long line, such as the pasted log in #703, the overlap step-back emitted shrinking copies of those short lines. The chunker now leaves room for the long line instead. Rebuilt from the same documents, the index sheds 174 chunks from 37 threads, #703 goes from 18 chunks to 8, and the retrieval eval is unchanged. Chunks whose text appears elsewhere in their thread fell from 243 to 69; the rest are real repeats, such as a script pasted twice.
  • One thread can fill the top 8. Long threads make many chunks, and nothing stops all of them from ranking at once. In the exact-error search in §4, all eight slots were #703; after the chunker fix it is six of eight. Grouping results by thread is the likely fix.
  • Docs only at the latest release. Code is version-pinned, docs aren't. A question about 1.0.1 still sees the 26.0.0 docs, as step 1 of the recorded run shows.
  • No test with reworded questions yet. The retrieval test only checks whether a thread's own opening post finds it (§11). Correct URLs from testers fill that gap.
  • The router's confidence check is coarse. “Found by both lists” only means each top-40 list contains the top hit. In the b=10 search, a thread ranked 23rd and 28th was enough to send the question one-shot.
  • Planned, in ROADMAP.md: an A/B test against open-weight models, an embed in the apps' Read the Docs pages, a custom domain, and a per-person rate limit before anything goes public.

§13 · Your turn

How to test it well

  • One question per chat. Start a new chat for a new topic. Follow-ups are welcome; they go to the agent.
  • Rate every answer, good ones too. Pick 👍 or 👎 first; the panel won't log without one.
  • Paste the correct source URL when you know it. It is the one field that turns your case into an automatic retrieval test.
  • Write a specific note. “It invented --foo; the flag is --bar” can be checked. “Not great” can't.
  • Mix the question types: a plain how-to, a pasted traceback, something version-specific (“on 1.0.1, …”), something that worked in one release and broke in the next, an error you know is in a closed issue, something no one has answered, and a follow-up.
  • Ask about the outputs you use, not only about running the pipelines: a flag, a derivative file, which output feeds your analysis.
  • Nothing personal or sensitive. Chats are saved on the server during testing.
